# Начало работы

> Подробный разбор. В [README](../README.ru.md) есть сжатый туториал; эта страница раскрывает требования,
> установку, первую задачу и обновление. Английская версия — [01-getting-started.md](01-getting-started.md).

## Что такое tms-pipeline

tms-pipeline — это дисциплина для AI-агентов: она проводит одну уже поставленную задачу от тикета до
проверенного кода, держа память агента чистой на каждом шаге. Вы устанавливаете её поверх существующего
проекта, после чего даёте агенту команды (скиллы) — а он по стадиям доводит задачу до готового кода.

Несколько слов, которые встретятся дальше:

- **скилл** — это команда вида `/tms-01-research`, которую вы даёте агенту, чтобы он сделал один шаг работы.
- **контекстное окно** — рабочая память агента: всё, что он сейчас видит и держит в голове. Чем больше в
  ней лишнего, тем хуже ответ. Главная идея пайплайна в том, чтобы на каждом шаге давать агенту только
  нужное, а не вываливать всю задачу разом.
- **AGENTS.md** — файл с настройками вашего проекта: где лежат задачи, на каком языке писать, команды
  тестов, ваши правила. Агенты читают его, чтобы знать специфику именно вашего репозитория.

Важно сразу понять, чем tms-pipeline **является** и чем **не является**:

- **Является** процессом, который ведёт одну задачу через восемь стадий до кода, готового к слиянию.
- **Не является** генератором проектов: он не придумывает функции, не строит приложение с нуля и не
  заменяет ваши продуктовые решения. Что строить — решаете вы.

Работа в основном идёт «на бумаге»: каждая стадия оставляет в папке задачи один текстовый документ
(`.md`) — тикет, исследование, дизайн, план, ревью, отчёт. Код пишется на стадии 04 (реализация); стадия
04b (код-ревью) может добавить исправления по тому, что нашли ревьюеры. Остановиться и решить вас просят
дважды: после дизайна (02) и на гейте (06). Полный обзор стадий — [в разборе стадий](04-stages-deep-dive.ru.md).

## Требования — прочитайте сначала

Поскольку tms-pipeline ставится **поверх существующего проекта**, до начала у вас должны быть:

- репозиторий с реальным исходным кодом;
- база документации — место, где живут долговечные знания о продукте и архитектуре: дерево `docs`, вики,
  хранилище Obsidian, что угодно;
- в идеале — бэклог (список задач, ожидающих выполнения).

Если у проекта пока нет ни документации, ни бэклога, включённые пустые шаблоны (`templates/docs-vault/`)
дадут стартовую структуру, но наполнить их реальными продуктовыми решениями — ваша работа, так, как вы уже
работаете.

### Если проекта ещё нет

Всё сказанное выше предполагает, что проект уже есть. Если вы начинаете совсем с нуля, для этого есть
отдельный скилл — **`/tms-new`**, разовая настройка нового продукта. Он проводит интервью, по одному
вопросу за раз, и в конце раскладывает ваши ответы в стартовый набор документов и бэклог.

`/tms-new` не придумывает продукт за вас: что строить — решаете вы, он лишь раскладывает ваши ответы по
местам. Это разовый запуск, а не одна из стадий пайплайна.

> **Какой скилл выбрать.** Проекта ещё нет (ни кода, ни задач) → `/tms-new`. Проект уже есть (код и/или
> документы на месте) → `/tms-init` (см. ниже). Если запустить `/tms-init` на пустом репозитории, он сам
> подскажет перейти на `/tms-new`.

## Шаг 1. Установка

Настройка намеренно разделена на две половины. Сначала работает **установщик** — обычная терминальная
программа, которая просто раскладывает файлы. Затем подключается **агент**: `/tms-init` читает ваш
репозиторий и заполняет настройки.

### Установщик

```bash
npx tms-pipeline
```

Или запустите самую свежую версию прямо с GitHub:

```bash
npx github:TmsNine/tms-pipeline
```

Установщик спрашивает только три вещи: язык, каким инструментом вы пользуетесь (Claude Code, Codex или
оба) и путь к проекту. Затем он:

- копирует скиллы, роли агентов и команду `/tms-init` в `~/.claude` и/или `~/.codex` (сначала
  спрашивает; для Claude Code можно отказаться и поставить скиллы через плагин, см. ниже);
- кладёт в проект стартовый `AGENTS.md`, а если вы пользуетесь Claude Code — ещё и `.claude/CLAUDE.md`.

Уже существующий файл он не перезаписывает, если не передать `--force`. Полезные флаги:

| Флаг | Что делает |
|---|---|
| `--yes` | Без вопросов, со всеми значениями по умолчанию. |
| `--dry-run` | Показать, что было бы записано; ничего не менять. |
| `--force` | Перезаписать существующие файлы проекта и установленные скиллы/агентов. |
| `--answers <file>` | Взять ответы из JSON-файла (так его вызывает `/tms-init`). |
| `--version`, `--help` | Показать версию или справку. |

### Или: плагин Claude Code

Для Claude Code есть второй способ получить скиллы и агентов — маркетплейс плагинов, прямо в Claude Code:

```text
/plugin marketplace add TmsNine/tms-pipeline
/plugin install tms-pipeline@tms-pipeline
/reload-plugins
```

**Для Claude Code выберите один путь — плагин или копирование установщиком, не оба**, иначе каждый скилл
окажется дважды. Плагин обновляется через `/plugin`; копию вы обновляете сами, запустив установщик заново
с `--force` (одна оговорка — в разделе [об обновлении](#обновление-с-01x)). Плагин не пишет `AGENTS.md` —
это сделает `/tms-init` на следующем шаге.

### Codex

Codex читает `AGENTS.md` напрямую и не имеет команды установки плагинов, поэтому его скиллы и агенты
должны лежать там, где Codex их ищет, — в `~/.codex`:

- проще всего: запустите установщик, выберите Codex и согласитесь на копирование — он скопирует
  `codex-skills/` → `~/.codex/skills/` и `codex-agents/` → `~/.codex/agents/`;
- вручную: `cp -R codex-skills/* ~/.codex/skills/ && cp -R codex-agents/* ~/.codex/agents/`.

Чем отличаются два инструмента — в [конфигурации](02-configuration.ru.md#codex).

## Шаг 2. `/tms-init` — заполнить настройки

Откройте проект в Claude Code или Codex и выполните:

```text
/tms-init
```

`/tms-init` читает ваш репозиторий (команды тестов и сборки — из манифеста пакета и настроек CI, формат
номера тикета — из истории git, существующие документы и бэклог) и **сам заполняет `AGENTS.md`**.
Спрашивает он только то, что не смог прочитать сам, — прежде всего, где лежит база документации.

Несколько полей требуют вашего решения и из кода не угадываются — например, какие изменения требуют
проверки безопасности, как разделены данные разных клиентов, как вы меняете схему базы данных, где лежит
список тестов, которые уже падают. `/tms-init` оставляет их помеченными `<<TODO>>` и отправляет вас в
[ручную настройку](05-manual-setup.ru.md) — там для каждого поля есть готовая подсказка.

### Или: заполнить `AGENTS.md` вручную

Если хочется сначала во всём разобраться: прочитайте [методологию](00-methodology.ru.md), скопируйте
`templates/AGENTS.template.md` в репозиторий как `AGENTS.md` (а для Claude Code —
`templates/CLAUDE.template.md` как `.claude/CLAUDE.md`) и замените плейсхолдеры сами — каждый объяснён на
странице [конфигурации](02-configuration.ru.md).

> Не уверены, что вписать в плейсхолдер? Не гадайте — попросите агента прочитать ваш код и предложить
> значение, а затем подтвердите или поправьте его.

## Шаг 3. Проверить установку

В Claude Code выполните `/help` или откройте список скиллов — там должны быть скиллы `tms-*`: `tms-run`,
`tms-00-ticket` … `tms-06-gate`, `tms-new`, `tms-ui-screen` и скиллы аудита. В Codex те же имена, только
скиллы аудита и рефакторинга пронумерованы (`tms-90-audit-scope` и так далее).

## Шаг 4. Первая задача

Возьмите одну настоящую задачу из бэклога и выполните:

```text
/tms-run <TICKET-ID>
```

`tms-run` проводит задачу через все восемь стадий, каждую в своём свежем контексте, и оставляет по одному
документу на стадию в папке задачи (по умолчанию `docs/<TICKET-ID>/`):

| # | Стадия | Документ | Ваше участие |
|---|---|---|---|
| 00 | Тикет | `00_ticket.md` | вы говорите, в чём задача |
| 01 | Исследование | `01_research.md` | — |
| 02 | Дизайн | `02_design.md` | **вы читаете и одобряете дизайн** |
| 03 | План | `03_plan.md` | его подписывает лид |
| 04 | Реализация | `04_implementation.md` | — |
| 04b | Код-ревью | `04b_review.md` | — |
| 05 | Отчёт о тестах | `05_test_report.md` | — |
| 06 | Гейт | `06_review_gate.md` | **вы решаете** |

Пайплайн ждёт вас после дизайна и на гейте; молчание никогда не считается согласием, и `go` пишет только
человек. Если удобнее идти по стадиям, запускайте скиллы стадий сами по порядку, начиная с
`/tms-00-ticket <TICKET-ID>`.

Чтобы увидеть, как выглядят документы, до запуска своей задачи откройте готовый пример в
[`templates/example-task/ACME-101/`](../templates/example-task/ACME-101/) — одна синтетическая задача,
пройденная от начала до конца.

## Обновление с 0.1.x

В версии 0.2.0 несколько скиллов переименованы и объединены. Установщик добавляет новые, но **старые
скиллы никогда не удаляет**, поэтому после обновления удалите вышедшие из употребления папки `tms-*`
вручную из `~/.claude/skills/` и `~/.codex/skills/` — полный список в [CHANGELOG](../CHANGELOG.md).

Затем поставьте новую версию: обновите плагин или запустите установщик заново с `--force`. Одна
оговорка: `--force` перезаписывает и `AGENTS.md` с `.claude/CLAUDE.md` вашего проекта. Сначала сделайте их
копию или укажите установщику пустую папку как путь к проекту — тогда заменятся только скиллы и агенты.
В конце снова запустите `/tms-init`, чтобы в `AGENTS.md` появились новые разделы, описанные в
[конфигурации](02-configuration.ru.md).

→ Что каждая стадия делает изнутри — в [разборе стадий](04-stages-deep-dive.ru.md). Какая модель
работает в какой роли — в [маршрутизации моделей](06-model-routing.ru.md).
