# Конфигурация

> Как подстроить tms-pipeline под ваш проект.
>
> tms-pipeline — это дисциплина для AI-агентов: она проводит одну уже поставленную задачу от тикета до
> проверенного кода, держа память агента чистой на каждом шаге. Чтобы делать это для *вашего* проекта,
> агентам нужно знать ваши правила: где лежат задачи, на каком языке писать, какими командами проверять
> код. Всё это хранится в файлах настроек — о них эта страница.
>
> Большую часть настройки делают за вас установщик (`npx tms-pipeline`) и скилл `/tms-init` — команда,
> по которой агент сам читает ваш репозиторий и заполняет настройки. Эта страница нужна в двух случаях:
> когда хочется настроить что-то вручную, и для значений, которые остаются пустыми (помечены `<<TODO>>` —
> заглушка, ждущая вашего решения). Английская версия — [02-configuration.md](02-configuration.md).

## Об инструментах: Claude Code и Codex

tms-pipeline работает поверх AI-инструмента — программы, в которой вы разговариваете с агентом.
Поддерживаются два: **Claude Code** и **Codex**. Нужен только один — выберите тот, которым уже
пользуетесь. Файл `AGENTS.md` общий для обоих; Claude Code дополнительно читает свой `.claude/CLAUDE.md`.
Различия между инструментами собраны ниже, в разделе [Паритет с Codex](#codex).

## Где живут настройки: AGENTS.md и CLAUDE.md

Агенты не зашивают в себя специфику вашего проекта — они читают её на ходу из двух файлов настроек:

- **`AGENTS.md`** (в корне репозитория) — главный файл настроек проекта: где лежат задачи, на каком
  языке писать, ваши команды и правила. Его читают оба инструмента.
- **`.claude/CLAUDE.md`** — правила, нужные только Claude Code: какой агент ведёт какую стадию, какая
  модель и какое усилие закреплены за каждой ролью, и дисциплина «без самовольного расширения» для
  автоматического режима. Он подключает `AGENTS.md` строкой `@./AGENTS.md`, так что всё из `AGENTS.md`
  действует и здесь. Заполнять вручную в нём нечего, кроме названия проекта в заголовке.

Начинайте с шаблонов `templates/AGENTS.template.md` и `templates/CLAUDE.template.md`. Замените каждый
`{{PLACEHOLDER}}` своим значением и уберите подсказки `<!-- -->` / `« »` (установщик и `/tms-init` делают
это за вас).

## Разделы AGENTS.md

Скиллы находят нужное в `AGENTS.md` по названию раздела, поэтому заголовки оставляйте как есть. Ниже —
что лежит в каждом разделе и какие значения вы в нём заполняете. Разделы без значений в правой колонке —
готовые правила: их можно оставить как есть или подправить.

| Раздел | Что в нём | Значения |
|---|---|---|
| *Operating Standard* | Язык вывода, кто читает результат, тихий режим работы, как задавать вопросы. | `OUTPUT_LANGUAGE`, `AUDIENCE_PROFILE` |
| *Repository Grounding* | Читать документы только когда нужно; коду верить больше, чем устаревшим документам. | `DOC_INDEX_HINT` |
| *Project Context Snapshot* | Что за проект, где лежит код, как хранятся и разделяются данные. | `PROJECT_ONE_LINER`, `CODE_LAYOUT_HINT`, `PERSISTENCE_AND_TENANCY` |
| *Documentation Base* | Где лежат знания о продукте, папки задач, бэклог и реестры; формат номера тикета. | `DOC_BASE_PATH`, `TASK_FOLDER_PATTERN`, `BACKLOG_LOCATION`, `TRIGGER_REGISTER_LOCATION`, `TRACEABILITY_LOCATION`, `TICKET_ID_FORMAT` |
| *Pipeline Execution* | Восемь стадий, их документы, два стопа владельца, File Ownership как жёсткая граница. | — |
| *Gate: who signs what* | `go` пишет только человек; когда лид может подписать `conditional_go`; когда гейт обязан идти к владельцу. | — |
| *Testing And Validation* | Ваши команды проверки, единая проверка задачи, список тестов, которые уже падают. | `TEST_CMD`, `TYPECHECK_CMD`, `LINT_CMD`, `BUILD_CMD`, `TASK_CHECK_CMD`, `KNOWN_TEST_DEBT_LOCATION` |
| *UI And Design* | Ваша дизайн-система и реестр принятых вами экранов. Удалите, если интерфейса нет. | `DESIGN_SYSTEM_HINT`, `ACCEPTED_SCREENS_LOCATION` |
| *Stage 04 and 04b* | Один исполнитель пишет весь план; один проход безопасности только по триггеру; до пяти свежих проходов ревью. | — |
| *Security Triggers* | Список изменений, которые включают проход безопасности. | `SECURITY_TRIGGERS` |
| *Database / Schema Migration Policy* | Как меняется схема базы данных. Удалите, если базы нет. | `MIGRATION_POLICY` |
| *Future Work Capture* | Куда попадают отложенные пункты и как группировать их, а не дробить на много тикетов. | — |
| *Pre-Launch Manual Action Capture* | Где записываются ручные шаги запуска и в какую часть плейбука. | `LAUNCH_PLAYBOOK_LOCATION`, `LAUNCH_STAGE_MAPPING` |

Остальные разделы (*Task Mode*, *Vertical And Horizontal Research*, *Root Cause Discipline*,
*Change-Surface Triggers*, *Minimal Sufficient Change*, *Acceptance Contract*, *Documentation
Discipline*, *Safety And Workspace Hygiene*, *Decision Rules*, *Completion Protocol*) — общие правила
работы, заполнять в них нечего.

## Значения, которые заполняют установщик и `/tms-init`

Сам установщик спрашивает только язык. Остальное из этого списка заполняет `/tms-init`, прочитав ваш
репозиторий, и спрашивает вас только о том, что не смог выяснить сам. Этот же список установщик
принимает в файле `--answers`.

| Плейсхолдер | За что отвечает |
|---|---|
| `OUTPUT_LANGUAGE` | Язык всего, что читает пользователь (отчёты, документы). |
| `AUDIENCE_PROFILE` | Кто читает результат — от этого зависит, сколько объяснять (например, нетехнический владелец или опытный инженер). |
| `PROJECT_ONE_LINER` | Что за проект и на каком стеке он сделан. |
| `TASK_FOLDER_PATTERN` | Где лежат папки задач (например, `docs/<TICKET-ID>/`). |
| `DOC_BASE_PATH` | Путь к базе документации (дерево docs, вики или хранилище Obsidian). |
| `BACKLOG_LOCATION` | Файл бэклога — единственный список задач, который считается главным. |
| `TICKET_ID_FORMAT` | Формат номера задачи, например `PROJ-123`. |
| `TEST_CMD` / `TYPECHECK_CMD` / `LINT_CMD` / `BUILD_CMD` | Ваши команды проверки кода: тесты, проверка типов, линтер, сборка. |
| `TASK_CHECK_CMD` | Одна команда, которая собирает, проверяет типы и прогоняет тесты каждого пакета, затронутого задачей. Её запускают стадии 03, 04, 04b и 05. Если такой пока нет, перечислите команды, которые она должна объединить; очень советуем завести один скрипт. |
| `LAUNCH_PLAYBOOK_LOCATION` | Где вы ведёте ручные действия перед запуском (плейбук запуска). |

## Значения, которые требуют вашего решения (остаются `<<TODO>>`)

Их нельзя надёжно вычитать из кода. Они остаются помеченными `<<TODO>>`, чтобы вы их заметили; на
странице [ручной настройки](05-manual-setup.ru.md) для каждого есть готовая подсказка.

- **`SECURITY_TRIGGERS`** — список изменений, которые включают проход безопасности. Если задача
  затрагивает что-то из этого списка, стадия 04 запускает одну проверку безопасности (только чтение) по
  готовому изменению, а стадия 04b берёт самого сильного ревьюера. Оставьте подходящие общие пункты и
  допишите точные пути к модулям, где они живут в вашем коде:
  - вход и авторизация: кто пользователь и что ему разрешено;
  - разделение по арендаторам (арендатор, tenant — отдельный клиент в общей системе; в приложении для
    одного пользователя их нет, этот пункт пропустите) и определение того, кто сейчас вошёл;
  - граница доверия: места, где данные приходят извне и должны проверяться;
  - секреты, ключи подписи и журналы аудита;
  - деньги: цены, ссылки на оплату, возвраты;
  - пути, по которым идут персональные данные (PII): имя, почта, телефон пользователя.

  (В старых шаблонах это значение называлось `PROFILE_C_TRIGGERS`; при обновлении переименуйте его.)
- **`KNOWN_TEST_DEBT_LOCATION`** — список наборов тестов, которые уже падают в основной ветке. Прежде
  чем назвать упавший тест новой поломкой, агент сверяется с этим списком — и читает его из основной
  ветки, а не из ветки задачи. Перечисленные наборы всё равно запускаются; список лишь объясняет, почему
  они красные.
- **`TRIGGER_REGISTER_LOCATION`** — реестр триггеров: находки, которые важны только при определённом
  событии («первый массовый импорт», «второй сервер»). Стадия 04b добавляет сюда строки, вместо того
  чтобы засорять бэклог тем, что пока не проблема. Это может быть раздел бэклога.
- **`ACCEPTED_SCREENS_LOCATION`** — для проектов с интерфейсом: список принятых вами экранов с их
  эталонными изображениями. Принятый экран — эталон: его изменение идёт через `tms-ui-screen`, а другая
  задача не переделывает его попутно. Удалите, если интерфейса нет.
- **`PERSISTENCE_AND_TENANCY`** — как хранятся ваши данные и как система определяет текущего
  пользователя или арендатора, чтобы не смешать данные одних с данными других.
- **`MIGRATION_POLICY`** — как вы вносите и фиксируете изменения схемы базы данных (если базы нет,
  удалите этот раздел).
- **`LAUNCH_STAGE_MAPPING`** — какое ручное действие в какую часть плейбука запуска попадает.
- **`TRACEABILITY_LOCATION`**, **`CODE_LAYOUT_HINT`**, **`DOC_INDEX_HINT`**, **`DESIGN_SYSTEM_HINT`** —
  необязательные подсказки, которые помогают агенту ориентироваться в проекте (подсказка про
  дизайн-систему — это путь к вашей дизайн-системе или библиотеке компонентов). Лишние удалите.

> Не уверены, что вписать? Не гадайте сами — попросите агента (Claude Code или Codex) прочитать ваш код и
> предложить значения, а затем подтвердите или поправьте их.

## Паритет с Codex

Здесь собраны различия между Codex и Claude Code. Если вы пользуетесь одним инструментом, этот раздел
понадобится, только когда перейдёте на другой.

- Codex читает `AGENTS.md` напрямую, подключать его отдельно не нужно.
- Файл-манифест плагина (он сообщает инструменту, какие есть скиллы и команды) лежит в
  `.codex-plugin/plugin.json` для Codex и в `.claude-plugin/plugin.json` для Claude Code.
- Скиллы в обоих инструментах — это `SKILL.md`, но в репозитории два дерева: `skills/` для Claude Code и
  `codex-skills/` для Codex. В них один и тот же метод и одни и те же имена стадий (`tms-00-ticket` …
  `tms-06-gate`, `tms-run`, `tms-new`, `tms-ui-screen`); в Codex скиллы аудита и рефакторинга
  пронумерованы (`tms-90-audit-scope` … `tms-96-ui-refactoring`).
- Роли агентов тоже лежат в двух деревьях: роли Claude Code — Markdown в `agents/`, роли Codex — TOML в
  `codex-agents/`. В Claude Code у каждой стадии свой агент с закреплённой моделью; в Codex агентов
  стадий нет — стадия работает на модели вашей сессии, и собственные настройки модели есть только у
  вспомогательных ролей (explorer, developer, reviewer, security и другие). Подробнее — в
  [маршрутизации моделей](06-model-routing.ru.md).
- Сам пайплайн в обоих одинаков: восемь стадий, один исполнитель на стадии 04, один проход безопасности
  по триггеру, до пяти свежих проходов ревью на 04b, два стопа владельца.

### Установка скиллов и агентов для Codex

У Codex нет команды вроде `/plugin install`, поэтому файлы нужно положить в `~/.codex` вручную или
полуавтоматически:

- **Полуавтоматически:** запустите `npx tms-pipeline` (или самая свежая версия с GitHub —
  `npx github:TmsNine/tms-pipeline`), выберите Codex и согласитесь на копирование. Установщик скопирует
  `codex-skills/` → `~/.codex/skills/` и `codex-agents/` → `~/.codex/agents/`. Если вы не пользуетесь
  Codex, установщик `~/.codex` не трогает.
- **Вручную:** `cp -R codex-skills/* ~/.codex/skills/ && cp -R codex-agents/* ~/.codex/agents/`.

Установщик не трогает уже существующие файлы проекта, скиллы, команды и роли агентов. Передавайте
`--force`, только если сознательно хотите заменить их версиями из пакета — включая ваш `AGENTS.md`.

`AGENTS.md` в любом случае остаётся в корне проекта, и Codex читает его напрямую.
